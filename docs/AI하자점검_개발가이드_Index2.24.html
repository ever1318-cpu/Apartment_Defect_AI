1단계 — 전문가 Gold 데이터셋 확정

  1. RDS에서 woohaja_defect_photo_tagged를 read-only로 추출한다.
  2. 전문가/점검매니저 입력, 최종승인 상태, 사진 연결, 5계층 코드 완결 행을 Gold 후보로 분리한다.
  3. 원본 사진은 변경하지 않고 원본·정제본·마스크/품질정보를 별도 경로에 둔다.
  4. 동일 defect_id, 동일 세대, 동일 현장·유사 사진이 서로 다른 분할에 섞이지 않도록 그룹 분할한다.
  5. 사진 누락, 중복, 흐림, 스티커만 찍힌 사진, 개인정보 노출을 별도 플래그로 관리한다.
현재 기반: 111,402장·42,782개 하자 그룹·5개 분류 과제의 태깅 데이터셋이 존재합니다. 먼저 이 데이터의 전문가 확정 여부와 사진 품질을 확정하는 것이 가장 중요한 선행 작업입니다.

3단계 — GPU 학습: ConvNeXt-Tiny 기준 모델

  1. 환경: Google Colab GPU 또는 사내 GPU에서 Python·PyTorch·timm·CUDA 환경을 준비한다.
  2. 학습: ImageNet 사전학습 ConvNeXt-Tiny의 특징 추출부를 미세조정하고, area/part/part_detail은 각각 분류 헤드로 둔다.
  3. 공종·원인: 첫 실험은 이미지 멀티헤드로 학습하되, 최종 추천은 점검자 의견·상세부위·유사사례를 결합한다.
  4. 증강: 회전은 건축 방향 정보를 훼손할 수 있으므로 제한하고, 밝기·노출·흐림·크롭·압축은 현장 조건에 맞춰 적용한다.
  5. 모델 선택: validation 손실 하나가 아니라 계층별 Macro-F1, Top-3, 전문가 수정률이 가장 좋은 체크포인트를 선택한다.
중요: 화살표·스티커가 섞인 사진을 무조건 삭제하지 않습니다. 원본 모델과 정제본 모델을 각각 학습해 실제 현장 사진 테스트에서 비교합니다. 스티커 자체가 하자 위치의 유용한 힌트일 수도 있기 때문입니다.

검증 세트분할 방법목적

시간 외부 검증최근 접수 기간을 테스트로 보류시공/사진 관행 변화 대응
오염 강건성스티커·화살표·흐림·야간 등 별도 표본현장 실제 성능 확인

필수 산출물: 계층별 혼동행렬, Top-1/Top-3, Macro-F1, 레이블별 표본 수, 미확신 보류율, 점검자 수정률, 원본 대 정제본 비교표.

5단계 — 모델 패키지화

  1. 최적 체크포인트, 레이블 매핑, 전처리 크기/정규화, 학습 데이터 버전, 평가 결과를 하나의 버전 폴더로 묶는다.
  2. PyTorch 기준 모델은 model.pt로 보존하고, 서버용은 ONNX 또는 TorchScript로 내보낸다.
  3. 모델 패키지에는 model_version, taxonomy_version, 각 레이블 코드와 표시명, 신뢰도 임계값을 포함한다.
  4. 학습에 사용한 레이블 매핑을 바꾸면 모델 버전도 반드시 새로 발급한다.

앱이 서버에 보내는 메타데이터에는 항상 model_version, AI 후보, 확정값, 확정자, 확정 시각을 분리 저장합니다.

6단계 — 서버 우선 연결

첫 운영 연결은 서버 추론 우선이 효율적입니다. ConvNeXt-Tiny 기준 모델은 정확도 실험·교체가 잦고, 5계층 재순위와 유사사례 검색은 서버가 더 적합합니다.

점검자 확정
  1. 기존 Field API와 별도로 /v2/ai/defect-classify 같은 AI 추론 API를 둔다.
  2. 입력은 근경·원경·스티커 사진, 점검자 설명, 동·호·공간·앵커, 앱 버전이다.
  3. 응답은 5계층별 Top-3 후보, 신뢰도, 유사사례 ID, 모델 버전이다.
  4. API 실패나 VPN 미연결이면 앱은 사진·메타데이터·추론 요청을 로컬 큐에 저장하고 나중에 재전송한다.

7단계 — 휴대폰 오프라인 추론

현장이 불안정하므로 장기적으로는 폰에서도 부위/현상 1차 후보를 낼 수 있어야 합니다. 다만 ConvNeXt-Tiny 원본은 노트10 같은 기기에서 용량·추론시간 부담이 있을 수 있습니다.

기기 방식권장 모델역할
서버ConvNeXt-Tiny 전체 정밀 모델5계층 재순위·유사사례·정확한 최종 추천
S25급INT8 양자화 ONNX/LiteRT 모델오프라인 1차 부위·현상 Top-3
노트10급MobileNetV3/EfficientNet-Lite 등 경량 보조 모델사진 유효성·대분류 후보, 서버 복구 후 정밀 분석

Android에는 ONNX Runtime Mobile 또는 LiteRT(TFLite) 중 하나만 선택해 통합합니다. 첫 단계는 서버 추론으로 정확도를 검증하고, 승인된 모델을 INT8 양자화해 S25·노트10 실기기에서 속도와 배터리를 시험한 후 오프라인 기능을 켭니다.

8단계 — 앱 화면 연동

  1. 하자사진 화면: 근경 + 원경 + 설명 스티커 사진을 로컬에 원자적으로 저장한다.
  2. 하자설명 화면: 사진 미니 2장과 점검자 의견을 함께 표시한다.
  3. AI 분석 추천: 서버/로컬 모델 결과를 5줄 이내로 표시하고, 신뢰도가 낮으면 “후보 선택”만 제공한다.
  4. 점검자가 AI 후보를 채택·수정·거절한 이력을 저장한다.
  5. 확정 저장 시 사진, 원문, AI 응답, 최종 코드, 전송 상태를 하나의 하자 레코드로 묶는다.

9단계 — 운영 검증과 재학습

Pilot 1전문가 Gold 소규모로 기준 모델·API 정확도 검증
Pilot 2점검매니저 현장 앱에서 AI 제안·수정률 측정
Pilot 3오프라인 큐·재전송·원경 누락 없는지 실기기 검증
Release모델 레지스트리 버전 승인 후 단계적 배포

재학습은 매일 자동으로 하지 않습니다. 월별 또는 충분한 확정 표본이 누적될 때, 기존 모델 대비 외부 검증 성능과 점검자 수정률이 개선된 경우에만 새 모델을 승인합니다.

권장 착수 순서

  1. RDS read-only 접속을 복원해 전문가 Gold 후보 조건과 완결률을 확정
  2. Gold 5,000~20,000건으로 ConvNeXt-Tiny 멀티태스크 기준 모델 재학습
  3. 외부 단지/시점 테스트와 원본·정제본 비교 보고서 작성
  4. AI 추론 API를 Field API와 분리해 서버 연결
  5. S25와 노트10에서 경량 오프라인 모델의 속도·용량·배터리 시험
  6. 현장 확정 피드백을 Gold 후보로 누적하고 승인형 재학습 운영
