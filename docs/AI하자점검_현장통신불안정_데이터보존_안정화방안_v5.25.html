현장 통신불안정 환경의 하자데이터 보존·전송 안정화방안 v5.25

작성일: 2026-08-03 · 대상: S25/노트10 현장 점검 앱, PostgreSQL Field API, VPN·무선망

결론 — 통신 성공을 전제로 저장하면 현장에서 사진과 메타데이터가 유실됩니다. 촬영 직후 휴대폰 내부에 사진과 메타데이터를 하나의 로컬 작업 단위로 먼저 확정하고, 서버 전송은 이후 재시도 가능한 별도 단계로 분리해야 합니다. 현재 앱의 Room 로컬 DB·동기화 대기열 구조를 이 원칙에 맞춰 강화하면 됩니다.

1. 목표 구조: Local-first, Sync-later

[카메라 근경/원경/스티커 사진] ↓ 즉시 저장(앱 내부 저장소) [파일 해시·촬영시각·동호수·위치 메타데이터] ↓ 하나의 SQLite 트랜잭션 [하자 레코드 + 사진 목록 + operationId + 전송대기열] ↓ 네트워크/VPN 정상? ─ 아니오 → 로컬 보관·자동 재시도 │ 예 ↓ [사진 재개 업로드] → [서버 검증] → [메타데이터 확정] → [완료 ACK] ↓ 로컬 대기열 COMPLETED 표시
사진 보존
근경·원경·설명 스티커 사진을 각 파일별로 저장하고, 한 장 실패가 다른 사진의 보존을 막지 않게 합니다.
메타데이터 보존
동·호/공용부, 위치, 5계층 분류, 점검자 원문, AI 추천, GPS·방향·촬영시각을 로컬 DB에 함께 확정합니다.
전송 독립
전송 실패는 저장 실패가 아닙니다. UI에는 로컬 저장 완료 · 전송 대기로 명확히 구분합니다.

2. 휴대폰 로컬 저장 안정화

대책구현 방식효과
원자적 사진 저장.tmp 파일에 완전 기록 후 파일 길이·해시 확인, 성공 시 최종 파일명으로 rename합니다.촬영 중 앱 종료·배터리 부족 때 손상 JPEG가 정상 사진으로 보이는 문제를 막습니다.
사진·메타데이터 묶음사진 파일이 존재하고 SHA-256이 계산된 경우에만 Room의 하자·사진·sync_queue를 하나의 트랜잭션으로 생성합니다.DB만 남거나 사진만 남는 불일치를 줄입니다.
복구 검사앱 시작 시 captures 폴더와 DB 사진 목록을 대조합니다. 파일만 있으면 복구 후보, DB 경로만 있으면 재촬영/오류 후보로 표시합니다.강제 종료 후에도 누락을 발견·복구합니다.
저장공간 감시여유 공간이 임계값(예: 2GB) 아래면 촬영 전 경고하고, 완료 전송 사진은 정책에 따라 저해상도 보관 또는 관리자 백업 후 정리합니다.용량 부족으로 인한 연속 촬영 실패를 예방합니다.
파일명과 내부 ID 분리표시 파일명은 101-1404_안방-천장_근경_20260803-142501.jpg처럼 사람이 읽게 하고, 중복 방지는 UUID/operationId로 처리합니다.파일명을 바꿔도 중복 전송과 데이터 충돌을 막습니다.

3. 불안정 VPN·무선망 전송 안정화

대책권장 방식주의점
연결 판정Wi-Fi/모바일 연결 표시만 보지 말고, 실제 /health 응답과 업로드 가능한 서버 응답을 확인합니다.VPN 아이콘이 켜져 있어도 서버가 응답하지 않을 수 있습니다.
재시도지수 백오프 + 무작위 지연: 10초, 30초, 1분, 3분, 10분… 앱 재시작·네트워크 복구 시 즉시 재시도합니다.모든 기기가 동시에 재시도하는 폭주를 피합니다.
업로드 재개사진은 파일 단위 또는 청크 단위로 재개 가능 업로드를 사용합니다. 서버는 받은 바이트·해시를 기록합니다.긴 사진 전송이 끊겨도 0%부터 다시 보내지 않습니다.
멱등성각 하자 묶음에 고정 operationId를 사용하고 서버는 같은 ID를 중복 저장하지 않습니다.응답을 못 받았을 때 재전송해도 중복 하자가 생기지 않습니다.
우선순위메타데이터·썸네일 → 근경 → 원경 → 스티커 순으로 보낼 수 있게 합니다.망이 다시 끊겨도 최소한 하자 존재·분류는 서버에서 확인됩니다.
WorkManager네트워크 연결됨 조건의 백그라운드 작업으로 전송하며, 앱을 닫아도 재개합니다.배터리 최적화 예외가 필요한 기기는 현장 배포 전 점검합니다.

4. 서버 측 확정 규칙

  • 서버는 사진을 안전 저장·해시 검증한 뒤에만 해당 사진을 완료 처리합니다.
  • 하자 메타데이터는 사진 업로드 상태를 참조하며, 사진이 아직 도착하지 않았어도 PENDING_MEDIA 상태로 먼저 보관할 수 있습니다.
  • 서버 응답은 operationId, 수신 사진 목록, 해시, revision을 포함합니다. 휴대폰은 이 응답을 받은 뒤에만 로컬 대기열을 COMPLETED로 바꿉니다.
  • 운영 전환 시 PC 폴더 저장 대신 객체 스토리지(S3 호환) 또는 백업 정책이 있는 파일 스토리지를 사용합니다. PostgreSQL에는 경로·해시·메타데이터를 저장합니다.

6. 우선 구현 순서

  1. 1순위 사진 원자 저장, 파일/DB 복구 검사, 로컬 저장 완료와 전송 대기 상태의 명확한 분리
  2. 2순위 operationId 기반 중복 방지, 자동 재시도·네트워크 복구 트리거, 실제 health 체크
  3. 3순위 청크/재개 업로드, 서버 해시 검증·ACK, 전송 우선순위
  4. 4순위 S25 실행상태 시뮬레이터에 전송 단계·실패 사유·마지막 성공 시각을 표시
  5. 5순위 비행기 모드, VPN 종료, 서버 재시작, 강제 종료, 저장공간 부족을 포함한 현장 복원력 시험

7. 현재 구현 기반과 보완점

현재 앱은 Room 로컬 DB와 sync_queue, 휴대폰 내부 사진 저장, VPN/서버 health 표시, 미전송 건수 표시의 기반을 갖추고 있습니다. 다음 구현에서 핵심은 전송 실패에도 하자 묶음 자체는 이미 로컬에서 확정되었다는 보장을 파일·DB·전송 응답까지 일관되게 강화하는 것입니다.
