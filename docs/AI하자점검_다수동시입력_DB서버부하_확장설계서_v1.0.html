다수 동시입력 DB·서버 부하 확장설계서 v1.0

작성일: 2026-08-03 · 적용 대상: 품질점검 매니저 20명, 입주자 사전점검 최대 2,000명

핵심 결론 — 앱이 사진을 API 서버와 PostgreSQL에 직접 동시에 밀어 넣는 구조는 2,000명에서 병목이 됩니다. 사진 업로드, 메타데이터 확정, AI 분석, 알림을 분리하고, 서버는 빠르게 접수만 완료한 뒤 큐 기반 비동기 처리로 넘겨야 안정적입니다. PostgreSQL은 업무 데이터의 권위 저장소로 유지하되, 대용량 이미지 파일 자체는 객체 스토리지에 둡니다.

1. 규모별 운영 시나리오

구분품질점검 매니저입주자 사전점검설계 판단
사용자약 20명, 장시간 집중 점검최대 2,000명, 특정 시간대 급증2,000명 기준으로 접수 계층을 설계하고 20명은 경량 모드로 운영
입력 패턴1건당 근경·원경·스티커 사진, 메타데이터 풍부의견·사진 1~2장 중심, 동시 제출 급증 가능사진 업로드와 DB 기록을 분리
가정 예시20명 × 분당 1건 = 분당 20건2,000명 중 10%가 10분 안에 제출 = 분당 20건 이상; 재시도 집중 시 훨씬 증가평균이 아니라 순간 피크와 재전송 폭주를 기준으로 큐·제한을 둠
위험현장 망 단절 후 동시 재전송특정 접수 시작 시간, 푸시 알림 후 동시 접속백오프·지터·업로드 슬롯 제한 필수

정확한 서버 수는 사진 용량, 피크 동시 업로드 수, AI 호출 시간, 서비스 목표(SLA)를 측정한 뒤 산정해야 합니다. 아래 구성은 해당 값을 측정·확장할 수 있는 안전한 기본 구조입니다.

2. 권장 전체 구조

[S25/노트10/입주자 앱] └ 로컬 DB·사진 저장 → API Gateway / Load Balancer ├ 인증·권한·요청제한 ├ 접수 API (메타데이터, operationId) └ 사전서명 업로드 URL 발급 ↓ [객체 스토리지: 원본 사진/썸네일] ↓ 이벤트 [메시지 큐 / 작업 대기열] ├ 미디어 검증·해시·썸네일 Worker ├ AI 이미지/LLM 분석 Worker ├ PostgreSQL 메타데이터 확정 Worker └ 알림·집계 Worker ↓ [PostgreSQL: 사용자·세대·하자·분류·상태] ↓ [조회 API / 관리자·입주자 화면]
API Gateway
인증, API 키/JWT, 속도 제한, 요청 크기 제한을 담당합니다. 앱 요청을 즉시 DB에 과도하게 연결하지 않습니다.
객체 스토리지
사진은 S3 호환 스토리지에 직접 업로드합니다. API 서버는 큰 파일 전송의 중계자가 되지 않습니다.
메시지 큐
AI 분석·썸네일·집계 같은 느린 작업을 분리합니다. 서버가 잠시 밀려도 접수는 유지됩니다.
PostgreSQL
트랜잭션 업무 데이터·상태·분류·감사기록을 담당합니다. 이미지 binary를 DB에 직접 저장하지 않습니다.

3. 단계별 부하 제어

단계서버 동작부하 안정화 규칙
① 로그인·권한짧은 토큰 발급, 등급별 권한 확인서버관리자/총괄/점검/소유주 권한을 토큰 claim으로 부여. 로그인 요청에도 IP·기기별 제한 적용.
② 하자 접수메타데이터와 operationId를 먼저 접수수 밀리초 수준의 짧은 DB 트랜잭션만 사용. 동일 operationId는 기존 결과를 반환해 중복을 막음.
③ 사진 업로드사전서명 URL로 앱→객체 스토리지 직접 업로드기기당 동시 업로드 1~2개, 재개 업로드·청크 업로드, 파일 크기·MIME·해시 검증.
④ 서버 확정사진 업로드 확인 후 상태를 MEDIA_READY로 전환사진 업로드 완료 전에는 하자를 PENDING_MEDIA로 보관. DB 잠금 시간 최소화.
⑤ AI 분석큐 Worker가 사진·텍스트를 비동기 처리사용자 저장 흐름을 AI 응답에 묶지 않음. AI 지연·실패 시 AI_PENDING으로 두고 재시도.
⑥ 조회·보고서읽기 API와 집계 조회캐시·읽기 전용 복제본·사전집계 테이블을 사용. 무거운 통계가 운영 쓰기 DB를 막지 않게 함.

4. PostgreSQL 설계 원칙

  • 연결 풀: API 인스턴스별 DB 연결 수를 제한하고 PgBouncer 또는 관리형 연결 풀을 사용합니다. 2,000명이 곧 2,000 DB 연결이 되면 안 됩니다.
  • 핵심 인덱스: operation_id unique, household_id + created_at, inspection_session_id + status, media_upload_id를 인덱싱합니다.
  • 상태 모델: LOCAL_ONLY → PENDING_UPLOAD → UPLOADING → MEDIA_READY → AI_PENDING → COMPLETED / RETRY / FAILED로 분리합니다.
  • 파티셔닝: 대규모 운영 시 하자·감사 로그는 프로젝트/단지 및 월 단위 파티셔닝을 검토합니다. 초기에는 과도한 파티셔닝보다 인덱스와 수명 정책이 우선입니다.
  • 감사성: 점검자 원문 의견, AI 결과, 최종 확정 분류와 변경 이력을 별도로 보존합니다.

5. 입주자 2,000명 피크 방어

문제대응
접수 시작 시 동시 로그인짧은 캐시 가능한 인증, 대기열 페이지 또는 시간대 분산 안내, 로그인·조회 API 분리
사진 동시 업로드객체 스토리지 직접 업로드, 앱의 업로드 슬롯 1~2개, 서버·스토리지에 크기 제한 및 업로드 URL 만료
망 복구 후 재전송 폭주기기별 지수 백오프+무작위 지연, 서버는 429/Retry-After를 명확히 반환, 큐 소비량 자동 확장
AI 호출 폭주·비용 증가접수 후 비동기 분석, 중복 사진 해시 캐시, 낮은 우선순위 배치 분석, 사용자 화면에는 분석 대기 상태 표시
보고서 조회로 DB 부하집계 결과 캐시·사전 집계, 페이지네이션, 원본 사진은 썸네일부터 제공

6. 가용성·보안·복구

영역최소 운영 기준

사진버전관리 객체 스토리지, 암호화, 수명 정책, 백업 지역/버킷 분리
큐재시도 횟수·dead-letter queue, 독성 메시지 관찰, 작업별 소비량 모니터링

8. 단계별 도입 로드맵

  1. 1단계 현재 FastAPI·PostgreSQL·로컬 대기열에 operationId, 상태 전이, 서버 429/Retry-After, 재시도 지터를 강화합니다.
  2. 2단계 사진을 객체 스토리지 직접 업로드로 전환하고 서버 파일 시스템 저장은 개발용으로만 유지합니다.
  3. 3단계 메시지 큐와 Worker를 도입해 AI·썸네일·통계를 비동기로 분리합니다.
  4. 4단계 부하 시험: 20명 지속 입력, 200명·2,000명 접수 버스트, VPN 복구 재전송을 자동 시험합니다.
  5. 5단계 운영 관제, 백업 복구 훈련, 역할 기반 관리 화면과 비용 관리를 정착합니다.

9. 권장 의사결정

20명 현장 점검 파일럿은 현재 로컬 우선 저장+PostgreSQL API를 안정화해 시작할 수 있습니다. 그러나 2,000명 입주자 동시 접수 전에 반드시 객체 스토리지 직접 업로드, 큐 기반 AI 처리, 연결 풀, 속도 제한, 재개 업로드, 부하 시험을 도입해야 합니다. 이 전환이 완료되면 통신 불량·피크 접속·AI 지연이 서로 영향을 주지 않는 운영 구조가 됩니다.
